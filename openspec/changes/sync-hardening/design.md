# 设计

## 决策

**D1 监听清单抽成 `SyncController.watchedTables(db)`，并把 `MergeService._tables`
改名为公开的 `syncedTables`。**
两边各写一份清单，正是这次漏掉 `operating_costs` 的原因。抽出来之后测试至少能
比对数量，改一边忘另一边会立刻红。

**D2 `/v1/snapshot` 收发都走流。**
`readAsBytes` + `expand((c) => c).toList()` 的写法把整库摊成逐字节的 List ——
几十 MB 的库在手机上就是几百 MB 的瞬时堆占用。改成 `IOSink.addStream` 与
`StreamedRequest`，内存占用与库大小解耦。

**D3 临时文件的删除放进 `finally`，GET 分支放进流的 `finally`。**
POST 是「写完 → 合并 → 响应」，失败点在任何一步都能删；GET 要先响应再把文件
当流发出去，只能在流的 `finally` 里删，否则响应还没读完文件就没了。

**D4 解绑走新端点 `/v1/unpair`，失败静默。**
只删本地行不叫解绑 —— 对方手里的 token 仍然有效。新端点需要令牌，语义是
「把你记的我删掉，并作废这张令牌」。对端关机是常态，解绑不能被它挡住。

**D5 失败也刷新，但只对「尝试过」的失败。**
`noPeer` / `offline` 时库根本没碰，刷新纯属白算。其余情况（包括推送失败）
可能已经合并过拉回来的数据，不刷新就是「同步了但界面没变」。

**D6 失败对端用进程内 Set 记录，不落库。**
落库要加列、加迁移，收益是重启后还记得 —— 但重启后本来就会重新试一遍，
成本不值。全被跳过时回退到原列表，避免对方后来开机了永远轮不到。

**D7 体积上限先看 `content-length` 再流式累计兜底。**
只在流里计数会在超限时直接 `break` 关连接，客户端正在写的 body 被打断，
连 413 都读不到（实测 `ClientException: Connection closed before full header`）。
声明长度已知时先 drain 再响应，客户端能正常收到 413。

## 风险

- 新端点让新旧版本不能互通解绑：旧端会 404，已按「失败就算了」处理。
- `drain()` 一个声明超大的请求体会白读流量 —— 但比留下半个文件和一条断掉的
  连接好；自家客户端的上限是 512 MB。
- 失败对端不落库，进程重启后会重新试一次关机的机器（多花 3 秒超时）。
